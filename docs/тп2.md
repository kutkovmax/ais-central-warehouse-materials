### 1. Назначение документа и принципы моделирования

Настоящий документ регламентирует состав, структуру, семантику и правила ссылочной целостности информационного обеспечения АИС «Склад-МехПром». Модель разработана в соответствии с требованиями ТЗ (`TZ-01.md`) и базируется на следующих принципах:

1. **Нормализация данных:** реляционная модель спроектирована в третьей нормальной форме (3NF), что исключает дублирование и транзитивные зависимости неключевых атрибутов.
2. **Строгая типизация партионного учёта:** ключевой учётной единицей является партия поставки (`batch`), неразрывно связанная с конкретным сертификатом качества и решением ОТК.
3. **Изоляция адресного пространства:** топологическое описание склада (`storage_cell`) отделено от динамических остатков (`location_balance`), что позволяет гибко менять схему стеллажей без искажения истории проводок.
4. **Непрерывный аудит изменений:** фиксация истории перемещений и списаний через транзакционные сущности журнала (`stock_movement_log`).

### 2. Концептуальная модель данных (ER-диаграмма предметной области)

Концептуальная модель отражает ключевые бизнес-сущности склада и характер связей между ними:

```
┌─────────────────┐       1..n        ┌─────────────────┐       1..n        ┌─────────────────────┐
│  Номенклатура   ├───────────────────┤ Партия поставки ├───────────────────┤  Остаток в ячейке   │
│      (sku)      │                   │     (batch)     │                   │ (location_balance)  │
└────────┬────────┘                   └────────┬────────┘                   └──────────┬──────────┘
         │                                     │                                       │
         │ 1..n                                │ 1..n                                  │ n..1
         ▼                                     ▼                                       ▼
┌─────────────────┐                   ┌─────────────────┐                   ┌─────────────────────┐
│ Ед. измерения   │                   │ Протокол ОТК    │                   │   Ячейка хранения   │
│     (uom)       │                   │  (qc_protocol)  │                   │   (storage_cell)    │
└─────────────────┘                   └─────────────────┘                   └──────────┬──────────┘
                                                                                       │ n..1
┌─────────────────┐       1..n        ┌─────────────────┐                              ▼
│ Требование цеха ├───────────────────┤ Строка требов.  │                   ┌─────────────────────┐
│ (issue_request) │                   │ (request_item)  │                   │    Зона склада      │
└────────┬────────┘                   └────────┬────────┘                   │   (warehouse_zone)  │
         │                                     │                            └─────────────────────┘
         │ n..1                                │ n..1
         ▼                                     ▼
┌─────────────────┐                   ┌─────────────────┐
│  Подразделение  │                   │ Партия списания │
│  (department)   │                   │ (связка batch)  │
└─────────────────┘                   └─────────────────┘
```

### 3. Логическая структура базовых сущностей

#### 3.1. Блок НСИ и топологии

##### 1. `uom` (Справочник единиц измерения по ОКЕИ)
* `id` (PK, INT): уникальный суррогатный идентификатор.
* `code` (VARCHAR(10), UNIQUE): код ОКЕИ (напр., `796`, `166`, `006`, `112`).
* `name` (VARCHAR(50)): краткое наименование (`шт`, `кг`, `м`, `л`).
* `description` (VARCHAR(100)): полное наименование по классификатору.

##### 2. `sku` (Номенклатурный справочник материалов)
* `id` (PK, BIGINT): внутренний системный ID.
* `article` (VARCHAR(64), UNIQUE): складской артикул (напр., `МЕТ-КРУГ-40Х-D50`).
* `name` (VARCHAR(255)): регламентное наименование ТМЦ.
* `category` (VARCHAR(50)): группа номенклатуры (`METAL_ROLL`, `FASTENERS`, `BEARINGS`, `PAINT_OIL`, `ASSEMBLY_PARTS`).
* `material_grade` (VARCHAR(100)): марка материала/стали (напр., `40Х`, `12Х18Н10Т`, `СЧ-20`).
* `standard_code` (VARCHAR(100)): ГОСТ/ТУ изготовления (напр., `ГОСТ 2590-2006`).
* `uom_id` (FK -> `uom.id`): базовая единица складского учёта.
* `unit_weight_kg` (NUMERIC(12, 4)): расчётная масса единицы (или погонного метра).
* `safety_stock` (NUMERIC(12, 3)): величина неснижаемого страхового остатка.

##### 3. `warehouse_zone` (Функциональные зоны склада)
* `id` (PK, INT): уникальный ID зоны.
* `code` (VARCHAR(10), UNIQUE): литерный код зоны (`A`, `B`, `C`, `Q`, `EXP`).
* `name` (VARCHAR(100)): наименование (`Крупногабарит и прокат`, `Стеллажи метизов`, `Изолятор ЛКМ`).
* `zone_type` (VARCHAR(30)): категория зоны (`STORAGE`, `RECEIVING_QUARANTINE`, `HAZARDOUS`, `DISPATCH`).

##### 4. `storage_cell` (Адресные ячейки склада)
* `id` (PK, BIGINT): внутренний ID ячейки.
* `address_code` (VARCHAR(32), UNIQUE): координатный код `[Зона]-[Ряд]-[Секция]-[Ярус]-[Ячейка]` (напр., `B-04-12-3-02`).
* `zone_id` (FK -> `warehouse_zone.id`): привязка к функциональной зоне.
* `rack_number` (INT): номер ряда/стеллажа.
* `section_number` (INT): номер секции.
* `tier_number` (INT): номер яруса (полки снизу вверх).
* `position_number` (INT): номер лотка/позиции на ярусе.
* `max_weight_kg` (NUMERIC(10, 2)): предельная грузоподъёмность полки ($M_{\max}$).
* `max_volume_m3` (NUMERIC(8, 3)): максимальный физический объём ($V_{\max}$).
* `cell_status` (VARCHAR(20)): статус (`FREE`, `PARTIALLY_OCCUPIED`, `FULL`, `BLOCKED`).

---

#### 3.2. Блок партионного учёта и контроля качества (ОТК)

##### 5. `supplier` (Справочник поставщиков)
* `id` (PK, BIGINT): идентификатор контрагента.
* `inn` (VARCHAR(12), UNIQUE): ИНН поставщика.
* `name` (VARCHAR(255)): официальное наименование организации.
* `contact_info` (TEXT): телефоны, адрес, реквизиты договора поставки.

##### 6. `receipt_order` (Приходный ордер / Заголовок поставки, форма М-4)
* `id` (PK, BIGINT): номер системного документа прихода.
* `doc_number` (VARCHAR(64), UNIQUE): бумажный/учётный номер приходного ордера М-4.
* `supplier_id` (FK -> `supplier.id`): поставщик ТМЦ.
* `incoming_invoice_num` (VARCHAR(64)): номер ТТН/УПД поставщика.
* `incoming_invoice_date` (DATE): дата товарной накладной поставщика.
* `created_at` (TIMESTAMP): дата и время физической регистрации груза.
* `created_by_user_id` (FK -> `app_user.id`): кладовщик-приёмщик.
* `status` (VARCHAR(30)): статус документа (`REGISTERED`, `IN_INSPECTION`, `COMPLETED`, `REJECTED`).

##### 7. `batch` (Партия материала)
* `id` (PK, BIGINT): внутренний суррогатный идентификатор партии (`Batch_ID`).
* `receipt_order_id` (FK -> `receipt_order.id`): привязка к приходной поставке.
* `sku_id` (FK -> `sku.id`): номенклатурная карточка.
* `batch_number` (VARCHAR(64)): заводской номер партии/плавки от изготовителя.
* `manufacture_date` (DATE): дата изготовления партии заводом.
* `expiration_date` (DATE, NULL): срок годности (обязателен для ЛКМ/масел Зоны C).
* `initial_quantity` (NUMERIC(14, 3)): первоначальный поступивший объём партии.
* `current_quantity` (NUMERIC(14, 3)): текущий остаток партии на складе (суммарный).
* `qc_status` (VARCHAR(30)): вердикт ОТК (`UNDER_CONTROL`, `ACCEPTED`, `REJECTED_QUARANTINE`, `SCRAPPED`).
* `barcode` (VARCHAR(64), UNIQUE): штрихкод маркировочного ярлыка (Code 128 / DataMatrix).

##### 8. `qc_protocol` (Протокол входного контроля качества ОТК)
* `id` (PK, BIGINT): номер протокола испытаний.
* `batch_id` (FK -> `batch.id`): контролируемая партия.
* `inspector_user_id` (FK -> `app_user.id`): инженер ОТК, проводивший замеры.
* `protocol_number` (VARCHAR(64)): официальный номер протокола заводской лаборатории.
* `inspection_date` (TIMESTAMP): дата и время вынесения заключения.
* `certificate_number` (VARCHAR(128)): номер паспорта качества/сертификата плавки завода.
* `certificate_file_path` (VARCHAR(512)): ссылка на PDF-скан сертификата в хранилище.
* `verdict` (VARCHAR(20)): решение (`PASSED`, `FAILED`).
* `notes` (TEXT): замеры твёрдости, химсостав, комментарии к дефектам.

---

#### 3.3. Блок динамических складских остатков и резервирования

##### 9. `location_balance` (Остатки партий по координатным ячейкам)
* `id` (PK, BIGINT): суррогатный идентификатор остатка.
* `cell_id` (FK -> `storage_cell.id`): физическая ячейка хранения.
* `batch_id` (FK -> `batch.id`): размещённая партия.
* `physical_quantity` (NUMERIC(14, 3)): фактический объём партии в ячейке.
* `reserved_quantity` (NUMERIC(14, 3)): забронированный под требования объём.
* *Ограничение бизнес-логики:*
  $$
  \text{physical\_quantity} \ge \text{reserved\_quantity} \ge 0
  $$
* *Уникальный индекс:* составной ключ `UNIQUE(cell_id, batch_id)`.

##### 10. `department` (Подразделения предприятия / Цеха-потребители)
* `id` (PK, INT): идентификатор цеха.
* `code` (VARCHAR(20), UNIQUE): код подразделения (`MC-1`, `SC-2`, `CPO`).
* `name` (VARCHAR(150)): регламентное наименование (`Механический цех № 1`).
* `responsible_person` (VARCHAR(150)): начальник/диспетчер цеха.

##### 11. `issue_request` (Требование-накладная на отпуск материалов, форма М-11)
* `id` (PK, BIGINT): системный идентификатор требования.
* `request_number` (VARCHAR(64), UNIQUE): внутризаводской номер требования М-11.
* `department_id` (FK -> `department.id`): цех-заявитель.
* `production_order` (VARCHAR(64)): шифр производственного заказа (насоса/компрессора).
* `created_at` (TIMESTAMP): время регистрации заявки в веб-кабинете.
* `created_by_user_id` (FK -> `app_user.id`): мастер цеха.
* `status` (VARCHAR(30)): статус жизненного цикла (`DRAFT`, `SUBMITTED`, `RESERVED`, `PICKING`, `ISSUED`, `CANCELED`).

##### 12. `request_item` (Спецификация требования цеха)
* `id` (PK, BIGINT): строка требования.
* `request_id` (FK -> `issue_request.id`): ссылка на заголовок требования.
* `sku_id` (FK -> `sku.id`): запрашиваемая номенклатура.
* `requested_quantity` (NUMERIC(14, 3)): запрошенный цехом объём.
* `allocated_quantity` (NUMERIC(14, 3)): фактически зарезервированный объём по FIFO.
* `issued_quantity` (NUMERIC(14, 3)): фактически отпущенный объём при выдаче.

##### 13. `request_allocation` (Конкретизация резервов по партиям и ячейкам)
* `id` (PK, BIGINT): запись резервирования.
* `request_item_id` (FK -> `request_item.id`): строка спецификации требования.
* `location_balance_id` (FK -> `location_balance.id`): конкретная ячейка и партия отбора.
* `quantity` (NUMERIC(14, 3)): забронированное количество.

---

#### 3.4. Блок аудита, инвентаризации и безопасности

##### 14. `stock_movement_log` (Журнал материальных проводок)
* `id` (PK, BIGINT): идентификатор складской проводки.
* `batch_id` (FK -> `batch.id`): перемещаемая партия.
* `source_cell_id` (FK -> `storage_cell.id`, NULLABLE): ячейка-источник (NULL при приходе).
* `target_cell_id` (FK -> `storage_cell.id`, NULLABLE): ячейка-приёмник (NULL при списании в цех).
* `quantity` (NUMERIC(14, 3)): объём перемещения/списания.
* `movement_type` (VARCHAR(30)): тип операции (`RECEIPT_PUTAWAY`, `INTERNAL_TRANSFER`, `PRODUCTION_ISSUE`, `INVENTORY_ADJUSTMENT`, `SCRAP`).
* `document_ref` (VARCHAR(64)): номер документа-основания (М-4, М-11, ИНВ-19).
* `performed_by_user_id` (FK -> `app_user.id`): исполнитель проводки.
* `timestamp` (TIMESTAMP): точная серверная метка времени операции.

##### 15. `inventory_sheet` (Ведомость циклической инвентаризации)
* `id` (PK, BIGINT): системный номер инвентаризационной описи.
* `sheet_number` (VARCHAR(64), UNIQUE): официальный номер ведомости ИНВ-3.
* `zone_id` (FK -> `warehouse_zone.id`): проверяемая зона.
* `start_date` (TIMESTAMP): начало ревизии.
* `end_date` (TIMESTAMP, NULL): завершение ревизии.
* `status` (VARCHAR(20)): статус (`IN_PROGRESS`, `REVIEW`, `APPROVED`).

##### 16. `inventory_item` (Результаты слепого пересчёта ячейки)
* `id` (PK, BIGINT): строка ревизии.
* `sheet_id` (FK -> `inventory_sheet.id`): опись.
* `cell_id` (FK -> `storage_cell.id`): пересчитываемая ячейка.
* `batch_id` (FK -> `batch.id`): пересчитанная партия.
* `expected_quantity` (NUMERIC(14, 3)): учётный остаток в системе.
* `counted_quantity` (NUMERIC(14, 3)): фактически сосчитанный ревизором объём.
* `discrepancy` (NUMERIC(14, 3)): вычисленное отклонение ($\text{Факт} - \text{Учёт}$).

##### 17. `app_user` и `user_role` (Пользователи и безопасность RBAC)
* `app_user`: `id`, `username`, `password_hash`, `full_name`, `is_active`, `department_id`.
* `user_role`: связка `user_id` и перечисления ролей (`ROLE_STOREKEEPER_RECEIVING`, `ROLE_STOREKEEPER_PICKING`, `ROLE_QC_INSPECTOR`, `ROLE_WAREHOUSE_HEAD`, `ROLE_SHOP_MASTER`, `ROLE_ADMIN`).

### 4. Матрица ссылочной целостности и каскадных ограничений (Foreign Keys)

| Родительская таблица | Дочерняя таблица | Внешний ключ (FK) | Правило ON DELETE | Инженерный смысл ограничения |
|---|---|---|---|---|
| `uom` | `sku` | `uom_id` | `RESTRICT` | Запрещено удалять единицу измерения, пока на неё ссылаются ТМЦ |
| `sku` | `batch` | `sku_id` | `RESTRICT` | Запрещено удалять карточку SKU, если по ней зафиксированы партии |
| `batch` | `qc_protocol` | `batch_id` | `RESTRICT` | Запрещено удалять партию при наличии оформленного протокола ОТК |
| `storage_cell` | `location_balance` | `cell_id` | `RESTRICT` | Нельзя удалить ячейку склада, пока в ней числится ненулевой остаток |
| `batch` | `location_balance` | `batch_id` | `RESTRICT` | Нельзя удалить партию, если она распределена по ячейкам |
| `issue_request` | `request_item` | `request_id` | `CASCADE` | При удалении черновика заявки М-11 удаляются все её строки |
| `request_item` | `request_allocation`| `request_item_id` | `CASCADE` | При отмене строки требования высвобождается программный резерв |

### 5. Выводы по модели данных

1. Спроектированная логическая модель состоит из **17 взаимосвязанных сущностей**, полностью покрывающих предметную область складского учёта насосно-компрессорного предприятия.
2. Архитектура таблиц исключает возможность нарушения принципов складской прослеживаемости: каждый физический грамм или штука материала в ячейке строго привязаны к номеру партии и протоколу ОТК.
3. Логическая модель является исчерпывающим базисом для разработки физической DDL-схемы PostgreSQL и миграций Flyway в документе **ТП-03 (`TP-03.md`)**.
